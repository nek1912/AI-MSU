Dataset and Cleaning

CERT r4.2 is a synthetic insider threat dataset released by the CMU CERT Division. It simulates 1,000 employees over 501 days and includes five logged activity sources plus red-team incident injections across three scenarios.

Activity sources

  • Logon Workstation and PC logon / logoff events with timestamps and machine IDs.
  • Device Removable and network device connections, relevant to data exfiltration scenarios.
  • File File access, copy, upload and transfer events across the monitored file system.
  • Email Internal and external email activity including size and attachment counts.
  • HTTP Web browsing and HTTP requests, used in job-search and data-discovery scenarios.

Exploratory Data Analysis

The feature tables in data/processed/ give a consistent picture of normal behaviour across the 1,000 users and reveal the structural signatures that Isolation Forest is intended to detect: rare-event counts, after-hours activity, and large or attachment-heavy email.

Activity distribution by source

Email and HTTP dominate the daily event volume (means of 5.25 and 56.76 events respectively), while device and file activity are sparse — present on only a minority of user-days. Sparse sources are informative for anomaly detection precisely because genuine Insider Threat scenarios often introduce device and file activity where none existed before.

After-hours activity share

After-hours logon (49.8%) and HTTP (38.8%) are common in the dataset, so a simple after-hours rule is not itself a strong signal. After-hours device (2.3%) and file (1.5%) activity, by contrast, are comparatively rare — making them high-value features when they do occur. These rates are computed from the 501,000 user-day rows in complete_daily_features.csv.

Email behaviour: size and attachments

The median email carries about 79.6 KB and no attachments. The mean is skewed upward by a small number of very large messages (max ≈ 1.29 MB). Scenario 3’s mass-alert email and job-search Scenario 2’s attachment-heavy exfiltration both exploit this tail.

The synthetic dataset was generated so that insider activity is intentionally rare relative to the normal population — the “dense needle” design of CERT r4.2. That design choice is what makes an unsupervised model appropriate: the anomalies we are looking for are a small minority of the data.

Model and Results

Isolation Forest is an unsupervised ensemble method. It builds a large number of random decision trees by repeatedly splitting the feature space on random thresholds. Observations that reach a leaf quickly — because they sit far from the dense bulk of the data — receive a high anomaly score. The modelling choice fits this project: we have 501,000 normal-looking observations and only 30 labelled incident windows, so a method that does not require a balanced training set is the natural fit.

Recall distinction

User-level recall (72.86%) measures how many of the 70 known insider users have at least one flagged day. Incident-window recall (44.29%) measures how many of the 70 known insider incident windows contain at least one flagged observation. A user can be flagged without their specific incident window being caught, so the two numbers are not interchangeable.

Detection by scenario (reported)

Reported per-scenario detection: Scenario 1 (Wikileaks leak) — 13 of 30 detected; Scenario 2 (job-site browsing and USB theft) — 8 of 30 detected; Scenario 3 (disgruntled administrator, keylogger, and masquerade) — 10 of 10 detected. Scenario 3’s strong detection is consistent with its behavioural signature: after-hours logon, device use, and unusual email activity all fall inside the model’s feature set.

Note

An anomaly flagged by Isolation Forest is a suspicious observation, not proof of malicious intent. Many flagged user-days will be benign outliers. The model is a prioritisation tool for a human analyst, not a classifier of guilt. This distinction is central to the forensic framing of the project.

Conclusion

Three findings summarise what the model achieved and where it fell short, drawn from the reported results and the feature-level analysis above.

  1. 1 What the model identified well Scenario 3 — the disgruntled administrator who installs a keylogger, transfers it via USB, and then masquerades as a supervisor — was detected in all 10 of its incident windows. Its behavioural signature (after-hours logon, device activity, and unusual email) maps directly onto the 12 baseline features, which is why the unsupervised model caught it so cleanly.
  2. 2 Where detection was weak Scenario 2 — job-site browsing followed by USB data theft — was detected in only 8 of 30 incident windows. The browsing behaviour is largely an HTTP phenomenon and can sit inside normal browsing volume; the theft itself is a device event that only appears on a single day. The model’s daily granularity gives it limited ability to connect a low-signal browsing ramp with a one-day exfiltration event.
  3. 3 What should improve next Three directions would strengthen the work: (1) enriching the feature set with user-history baselines — comparing a day’s activity to the same user’s own past rather than to the global population; (2) modelling sequences or ramps rather than single days, so that slowly escalating browsing and device use can be connected; and (3) running an independent temporal evaluation on a held-out portion of the timeline to check that the reported recall figures generalise rather than reflecting the specific contamination and threshold used here.

Limitations

This dashboard presents results from a synthetic dataset released by the CMU CERT Division. CERT r4.2-2 is a “dense needle” variant with many injected incidents, which is useful for method development but does not by itself represent the class balance of a real organisation. Three limitations are especially relevant for the viva.

  • Daily incident labels The feature tables carry no per-day ground-truth label; the incident-window labels used for evaluation come from the separate red-team answer files. A confusion matrix computed at daily granularity therefore depends on how incident windows are mapped onto individual days.
  • Scenario differences The three scenarios differ sharply in behavioural footprint, so a single recall figure obscures large differences in how detectable each one is. Scenario-wise reporting is more honest than an aggregate.
  • Independent temporal evaluation The reported results were produced on the full dataset with a contamination parameter set to 1.0%. An independent temporal holdout would be needed to show the model’s performance holds up when it cannot see the incident period during training.
