Insider Threat Detection

Behavioural anomaly analysis using the CERT r4.2 dataset.

The system transforms user activity logs into daily behavioural features and uses Isolation Forest to identify unusual user-day observations. Detected anomalies are compared with known incident records to evaluate detection performance.

Two kinds of recall

User-level recall (72.86%) asks: was a known insider flagged on any day? Incident-window recall (44.29%) asks: was an anomaly detected during the labelled incident window? A user can be flagged at least once and still miss the actual incident period. These measure different things and are not interchangeable.

Result summary

The baseline identifies a substantial proportion of known insider users, but detection varies across scenarios. Detecting a user at least once does not guarantee that the model detects the associated incident.

Date coverage

501 distinct dates from 2 January 2010 to 17 May 2011. Every user appears on every date in the complete feature grid (1,000 users × 501 dates = 501,000 user-days).

Raw events versus user-day observations

Raw event records describe individual moments: one logon, one file open, one email. A user-day observation summarises everything one user did on one date into a single row of 12 feature values. The 32.77 million valid raw records above become 501,000 model rows. Most of those rows are zero-filled because the model requires a complete user × date grid: a zero means no event was recorded for that user on that day, which is not the same as proof that the person did nothing in the real world.

Decisions, stated plainly

  • The missing-value and duplicate checks in notebook 02 were run on a 10,000-row sample of logon.csv, which showed 0 missing values and 0 duplicate rows. This does not prove the full files are free of missing values or duplicates; the full-file check was not recorded.
  • During feature aggregation, rows with an unparseable date or a missing user identifier are dropped. The count of dropped rows is not recorded, only the count of valid rows kept.
  • Email size and attachment fields are coerced to numbers, with unparseable values replaced by 0.
  • The complete feature grid is zero-filled: every user has a row for every one of the 501 dates. A zero means no event of that type was recorded for that user on that day in the source logs. It does not prove the user had no real-world activity, and weekend or holiday zeros are indistinguishable from inactivity zeros.
  • Raw CSV files are never edited. Cleaned copies are written to the processed folder only.

Feature transformation

Before training, all 12 feature columns were transformed with log1p(x) = ln(1 + x) (verified in notebook 06: X = np.log1p(X)). This reduces the influence of extreme values such as very large email sizes. The transform is applied to model input only; stored feature values remain in their original units.

Feature-quality considerations

  • email_external_email_count is not used in the baseline model and should stay out of it until its external-recipient logic is correctly defined and validated.
  • http_unique_pcs and email_unique_pcs were found to be highly correlated in earlier analysis and should be reviewed before either is included. Neither is in the current baseline.
  • The psychometric personality attributes (OCEAN scores) are not part of the baseline model; they were excluded from model_cols. This dashboard makes no claim that personality data influenced any prediction.

Model explorer

Isolation Forest identifies observations that differ from the broader dataset. Observations that are easier to isolate receive stronger anomaly scores.

How Isolation Forest works, briefly

The model builds random decision trees that split on feature values. Points that end up alone in small branches were easy to isolate; points that share branches with many others were not. An observation's anomaly score summarises how quickly it gets separated from the crowd. This is unsupervised: the model never sees the incident labels during training, so labels can only be used afterwards for evaluation.

What contamination means

Contamination (0.01) is the model's assumed anomaly proportion used to place its fitted classification threshold. It is a setting, not a measurement: it does not mean 1% of users are malicious, and it does not reflect the true insider rate in the dataset.

Reading the score

The score convention here is anomaly_score = −decision_function(X), so higher scores indicate more anomalous observations. A flag means the observation looked unusual relative to the rest of the dataset. It does not describe intent and does not confirm wrongdoing.

Two units of analysis

User level

51 of 70 known insider users were flagged at least once (72.86%). One flagged day anywhere in the dataset counts the whole user as detected. Of the 171 flagged users, 51 are known insiders, so 29.82% of flagged users appear in the ground truth; the rest are unlabelled and may be ordinary variability.

Incident level

31 of 70 incidents were detected (44.29%). An incident counts as detected only if the model flagged that user during the labelled incident window. This is the stricter and more operationally meaningful test.

Day-level approximation

Incident windows carry timestamp precision, but predictions exist only at daily resolution, so windows were converted to daily labels: any user-day date falling inside a window counts as an incident day. Day-level evaluation is therefore an approximation of timestamp-level behaviour, and short incidents can be diluted inside a full calendar day of activity.

View metric formulas
  • Precision = TP ÷ (TP + FP) — of flagged user-days, the share inside a labelled window
  • Recall = TP ÷ (TP + FN) — of incident-window user-days, the share flagged
  • Specificity = TN ÷ (TN + FP) — of ordinary user-days, the share left unflagged
  • F1 = 2 × precision × recall ÷ (precision + recall)
  • Accuracy = (TP + TN) ÷ all user-days

The trade-off

At the 99th percentile the model raises 5,010 alerts and catches 4.44% of incident-window days. At the 95th percentile it raises 25,050 alerts and catches 19.29%. Five times the workload buys roughly four times the incident-day coverage. Choosing a threshold is an operational decision about how much review capacity exists, not a property of the model.

Limitations and future work

What these results do and do not prove.

Limitations

  • The model flags unusual behaviour, not proven malicious intent. Nothing in the pipeline establishes motive.
  • Detection performance differs substantially by incident scenario: 43.33% for Scenario 1, 26.67% for Scenario 2, and 100% for Scenario 3. A single headline recall number hides this spread.
  • A user can be flagged outside the actual incident window. User-level recall (72.86%) credits such flags; incident-window recall (44.29%) does not.
  • Daily labels approximate timestamp-based incident periods. Day-level confusion-matrix cells inherit that approximation.
  • The model was trained on the full period, which includes the incident windows later used for evaluation. This is not a fully independent, deployment-style evaluation, and it flatters the model: it saw the incident days' feature values while fitting.
  • Zero-filled feature rows require careful interpretation. A zero means no recorded event, not verified inactivity.
  • Feature definitions and correlations need continued review, including the two known issues on the Feature engineering page.
  • The ground truth only labels 70 users. All other 930 users are treated as unlabelled, not verified benign, so false-positive counts are upper bounds.

Future work

  • Improve behavioural feature definitions, including validated external-recipient logic for email.
  • Investigate why Scenario 2 incidents were frequently missed: the long windows and subtle single-source behaviour of that scenario deserve a dedicated analysis.
  • Evaluate thresholds using a defined validation procedure rather than choosing a percentile by inspection.
  • Train on a background period and evaluate on a later period, so the evaluation reflects deployment conditions.
  • Compare performance against a clearly documented baseline, such as random flagging at the same alert rate or a simple per-user z-score rule.

These are proposed directions. None of them has been carried out in this project.
